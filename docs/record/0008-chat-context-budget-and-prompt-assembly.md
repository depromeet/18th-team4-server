## 한 줄 요약

gpt-4o-mini 로 장기 채팅을 운영할 때, 모델의 **명목 컨텍스트 창(128K)을 다 쓰는 대신 유효 입력을 8~12K(상한 16K)로 묶는다.** 긴 컨텍스트 연구들이 "명목 길이 ≠ 품질이 유지되는 길이"이고 특히 중간 정보가 희석됨을 반복 확인하기 때문이다. 프롬프트는 **[고정 base+책][저변동 누적 요약]을 한 system 메시지에 임베드**하고, **매 턴 바뀌는 최신 원문 대화 + 현재 메시지를 역할 태그가 달린 messages 로** 뒤에 싣는다. 이 배치는 프롬프트 캐시(고정→저변동→변동)와 "중요한 것을 강한 위치(끝)에" 두 목적을 동시에 만족한다. **현재 설정값이 이미 이 목표에 앉아 있어 재튜닝이 아니라 의도의 명문화가 목적이다.**

## 배경 — 명목 128K 를 다 쓰면 안 되는 이유 (연구 근거)

모델이 받는 최대 입력(128K)은 "API 가 거부하지 않는 크기"이지 "답변 품질이 안정적으로 유지되는 크기"가 아니다. 네 갈래 연구가 이를 뒷받침한다.

- **Lost in the Middle (TACL 2024).** 관련 정보가 입력의 **앞·뒤에 있을 때 활용이 높고, 중간에 있으면 크게 떨어진다.** 긴 입력을 robust 하게 쓰지 못한다는 결론. → 채팅 이력을 통째로 넣으면 중간의 중요 맥락이 희석된다.
- **RULER.** 32K 이상을 "지원한다"는 모델 중 32K 에서 만족스러운 성능을 낸 건 절반가량. 단순 needle-in-a-haystack 은 잘해도 **입력 길이·태스크 복잡도가 오르면 크게 저하.** → 명목 길이와 실사용 길이는 다르다.
- **NoLiMa (ICML 2025).** 128K 지원 주장 13개 모델 평가에서 **32K 에서 11개가 짧은 길이 성능의 50% 미만**으로 하락, GPT-4o 도 99.3% → 69.7%. → 상위 모델도 32K 에서 무너지므로, 더 약한 **mini 로 32K+ 를 기본 경로로 잡는 건 위험**하다.
- **LongBench.** 장문 QA·요약·코드 등 종합 이해 벤치마크에서 상용 모델도 장문에선 어려움. → "키 하나 찾기"가 아니라 사용자 선호·이전 발언·현재 질문을 종합해야 하는 채팅은 이 난이도에 가깝다.

우리 채팅 모델은 **gpt-4o-mini**(`application-dev.yml`)라 이 신중함이 특히 적용된다.

## 결정

### 1. 유효 입력 목표 8~12K, 상한 16K (명목 128K 를 기본 경로로 쓰지 않는다)

연구를 보수적으로 해석한 실무 밴드:

| 입력 토큰 | 해석 | 판단 |
|---|---|---|
| ~4K | 대부분 대화에서 안정 | 최신 대화만으로 충분 |
| 4K~8K | 실무 챗봇에서 안전 | 기본 recent window |
| 8K~16K | 긴 맥락을 넣되 관리 가능 | summary + recent raw 구조의 상한 |
| 16K~32K | 처리 가능하나 정보 희석 리스크 | 필요할 때만 |
| 32K+ | 성능 저하가 명확히 관찰 | 기본 경로 비추천 |
| 64K~128K | "수용 가능"이지 "품질 안정" 아님 | 문서 분석 등 특수 기능 한정 |

→ 답변 생성 기본 **입력 목표 8~12K, 상한 16K**.

### 2. 프롬프트 조립 구조 — system 임베드 + 역할 태그 messages

`AiChatClientImpl` 이 만드는 최종 요청은 두 덩어리다:

```
system 메시지 1개 = [base 프롬프트] + [# 대화 대상 도서] + [# 이전 대화 요약 {누적 요약}]
messages         = [요약 반영 지점 이후 최신 원문 대화(USER/ASSISTANT ...)] + [현재 USER 메시지]
```

- **누적 요약은 별도 메시지가 아니라 system 안에 임베드**된다. 배치 순서가 `base(고정) → 책(세션 고정) → 요약(요약 갱신 때만 변동)`이라, **프롬프트 캐시**가 고정 접두부를 재사용하고 변동은 뒤로 몰린다. 매 턴 바뀌는 최신 원문은 messages 로 따로 실어 캐시 경계를 명확히 한다.
- **최신 원문 대화**는 `assembly-recent-raw-max-tokens`(8000) 안에서 newest-first 로 담고 턴 경계로 정렬(USER 시작). **현재 사용자 메시지는 messages 맨 끝에 append**(`AiChatMessageSendService`).

### 3. 이 구조가 Lost in the Middle 을 거스르지 않는 이유

프롬프트 위치별 강약과 우리 배치가 맞물린다:

| 위치 | 내용 | 강약 |
|---|---|---|
| system 앞 | base 프롬프트(871 토큰) | 시작(강) |
| system 중 | 책 정보(~50 토큰) | 시작(강) |
| system 끝 | **누적 요약(1~2K)** | **중간(약)** |
| messages | 최신 원문 대화(≤8K) | 끝(강) |
| 맨 끝 | 현재 메시지(≤~0.75K) | 끝(강) |

**이번 턴에 가장 중요한 최신 원문 + 현재 질문이 가장 강한 끝 위치**에, **저충실도 압축인 누적 요약이 약한 중간**에 놓인다. 요약은 정밀 활용을 기대하지 않는 배경 블록이라 약한 자리에 둬도 손해가 작다. 이 사실은 **요약을 크게 키울 이유가 없다**는 원리적 근거이기도 하다(어차피 모델이 제일 안 보는 자리다).

### 4. 예산 계상 — 게이트가 세는 payload

전역 게이트(`OpenAiRateLimitGuard`)는 **system 전문 + 모든 history(현재 메시지 포함) + 예약 출력**을 센다(`AiChatClientImpl`). 실측·설정값 기준 최악 입력:

```
base 871 + 책 ~50 + 요약 ≤~2,000 + 최신 원문 ≤8,000 + 현재 ~750 ≈ 11.7K (입력)
+ 예약 출력 512 (tokenBudget.estimatedOutputTokens)  →  요청 봉투 ~12.2K
```

목표(8~12K) 안, 상한(16K) 아래. **현재 설정값이 이미 이 목표를 실현**하고 있어 config 재튜닝은 불필요하다. 이 기록의 목적은 "왜 이 값인가"를 남겨 **명목 128K 를 근거로 무심코 recent-raw 를 32K+ 로 올리는 되돌림을 막는 것**이다.

## 관련 설정값 (application.yml `ai-chat.context`)

| 키 | 값 | 역할 |
|---|---|---|
| `assembly-recent-raw-max-tokens` | 8000 | 조립기가 한 호출에 실을 최신 원문 최대(안전핀). 밴드 상단 |
| `keep-recent-raw-tokens` | 2000 | 워커가 요약 않고 남길 최신 원문(요약 하한) |
| `summarize-trigger-token-threshold` | 4000 | 이 이상이면 요약 job 적재 |
| `summary-estimated-output-tokens` | 800 | 요약 호출 출력 추정(게이트 예약용) |
| (`tokenBudget.estimatedOutputTokens`) | 512 | 채팅 답변 예약 출력(게이트 계상) |

## 버린 / 미룬 대안

- **명목 128K 창을 그대로 활용** — mini 에선 연구상 품질 붕괴(NoLiMa·RULER). 기본 경로로 부적합. 128K 급 입력은 문서 분석 같은 특수 기능에 한정.
- **누적 요약을 크게(수 K 이상) 유지** — 약한 중간 위치라 활용도 낮고, 중간을 부풀려 Lost-in-the-Middle 리스크만 키운다. 1~2K 로 유지(결정 3).
- **총 입력에 하드 상한 가드를 코드로 강제 — 미룸.** 지금은 구성요소 합이 암묵적으로 ~12K 로 묶여 16K 아래라 급하지 않다. 다만 누적 요약 길이가 조립 시점에 하드 캡되진 않으므로(요약이 비정상적으로 길어지면 중간이 부푼다), 필요 시 "총 입력 16K 초과 시 최신 원문부터 축소" 가드를 얹는 걸 후속으로 둔다. **되살릴 트리거**: 감사 로그의 prompt 토큰이 상한에 반복 근접하면.

## 검증

base 프롬프트 토큰은 앱과 동일한 jtokkit(o200k_base)으로 실측(871). 실제 요청별 prompt/completion 토큰은 스트림 마지막 청크의 usage 로 감사 로그(`AiPromptAuditLogger`)에 남아, 운영에서 실제 입력 봉투가 이 예산 안에 있는지 사후 확인할 수 있다.
