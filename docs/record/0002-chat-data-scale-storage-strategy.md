# 0002 — 대용량 채팅 데이터 저장/조회·쓰기 전략 (현재는 MySQL 유지)

- **상태**: 채택
- **날짜**: 2026-07-02
- **관련**: 이슈 #103(AI 채팅 동시성 개선), [0001](0001-aichat-title-generation-scheduler-bulkhead.md)
- **바뀐 코드**: 없음 — 방향을 정하는 기록이다. 후속 최적화(컨텍스트 조회 캐싱)는 별도 이슈로 진행한다.

## 한 줄 요약

채팅 메시지는 분리 후보가 맞지만, **지금은 MySQL 단일 프라이머리에 그대로 둔다.** 실제 쓰기 병목이
관측되기 전까지 별도 NoSQL(Dynamo/Scylla) 을 도입하지 않고, 미래 분리를 싸게 만드는 **설계 규율만
유지**한다. 이 기록은 그 판단 근거와, 높은 부하를 가정했을 때의 확장 설계 지도를 함께 남긴다.

## 배경 — 이 논의가 시작된 지점

"채팅을 보낼 때마다 누적 대화 이력을 조회해 LLM 에 보내는" 구조에서, **대용량 트래픽 시 조회/쓰기
부하를 어떻게 효율적으로 다룰지**를 고민하며 시작했다. 현재 실제 부하는 매우 적으므로, 이 기록의
확장 설계 부분은 **"높은 부하를 가정한 학습·대비 설계"** 성격이다 (지금 당장 구축 지시가 아니다).

현재 채팅 저장 스키마(관련 엔티티 4개: `AiChatSession`, `AiChatMessage`, `Summary`, `SummaryJob`)의
핵심 성질:

- 모든 관계가 **JPA 연관관계 없이 순수 `Long` 논리 FK** (DB 제약 없음, cascade 는 앱이 서브쿼리로 수동 처리)
- `AiChatMessage` 가 직접 엮인 건 **`session_id`(→세션) 하나뿐**. 책·사용자·감상문·작업은 전부
  메시지가 아니라 **세션에 매달려** 있다.
- 뜨거운 읽기 = "세션별 최근 원문 꼬리", 매 메시지 전송마다 재조회
  (작성 당시 근거는 `context-window.max-turns: 20` 고정 40개였음. 이후 컨텍스트 압축 도입으로
  개수 고정 창 → 토큰 예산 기반 원문 꼬리 + 누적 요약으로 교체됨 — 뜨거운 읽기가 세션당 여전히
  유계라는 이 결정의 전제는 그대로다. 상세는 [docs/domain/ai-chat.md](../domain/ai-chat.md))
- 쓰기 = append-only (auto-inc PK → 순차 삽입)
- 요약되면 세션이 `LOCKED` → 그 세션 메시지는 **읽기 전용 콜드**가 되고 파티션 크기 상한이 잡힌다

## 결정

**1차 선택: MySQL 유지.** 근거:

1. **현재 병목은 DB 쓰기 처리량이 아니다.** 이 앱의 바인딩 제약은 수 초~수십 초 살아있는
   **OpenAI 스트리밍 연결**·토큰 한도·업스트림 연결 관리다 (#103). 메시지를 초당 수천 건 쓸 만큼
   생성되려면 그 전에 LLM 쪽이 먼저 무너진다.
2. **단일 프라이머리 쓰기 천장이 이 앱 규모엔 매우 높다.** 작은 row 기준 중간급 인스턴스가 수천
   INSERT/초. 대화 1턴 = 2 INSERT 라, 1,000 INSERT/초 ≈ 동시 활성 대화자 ~1.5만 명 규모. 닿기 어렵다.
3. **NoSQL 분리는 쓰기 수평 확장을 주지만 트랜잭션·조인·운영 단순성을 잃는다.** 소유권 서브쿼리
   (`AiChatMessage → AiChatSession → UserBook → user_id`)와 크로스-저장소 원자성을 포기해야 한다.

## 버린 대안 — 지금 NoSQL(Dynamo/Scylla) 도입

접근 패턴이 `(파티션키=sessionId, 정렬키=created_at#id)` 로 wide-column 저장소에 **정확히 맞아떨어지는
것은 사실**이다. Dynamo/Scylla 의 명확한 이점도 실재한다:

1. **쓰기를 노드 추가로 수평 확장** — MySQL 단일 프라이머리가 근본적으로 못 하는 유일한 것
2. **조회 지연이 전체 데이터 크기와 무관** — 파티션 하나만 읽으므로 O(파티션), 데이터가 100억 row 로
   쌓여도 "최근 40개" 비용이 거의 일정 (MySQL 은 테이블 비대화로 느려질 수 있음)
3. **테이블 비대화 관리(파티셔닝·아카이빙)가 통째로 불필요** — TTL 로 콜드 데이터 자동 만료

**그럼에도 지금은 도입하지 않는다:** 위 이점 3가지는 **전부 높은 스케일에서만 실체화**된다. 현재
부하에선 실질 이득이 0이고 복잡성만 는다. 총 쓰기량을 줄여주지도 않는다("여러 sessionId 로 흩어짐"은
총량 감소가 아니라, 여러 노드에 고르게 퍼뜨릴 수 있게 만드는 전제일 뿐이다). 관계형의 트랜잭션·조인·
유연한 조회를 잃는 대가만 먼저 치르게 된다.

## 미래 분리를 싸게 만드는 규율 (지금 지킬 것)

분리 결정 시점이 오면 매끄럽게 넘어가도록, 아래 규율을 **유지**한다. 대부분 이미 지켜지고 있으므로
"새 작업"이 아니라 "깨지 않기"에 가깝다.

- **메시지를 JPA 연관관계로 직접 탐색하지 않는다** — 이미 `@ManyToOne`/`@OneToMany` 없음. 유지.
- **메시지 접근은 서비스 계층(`AiChatHistorySearchService`/`AiChatMessagePersistService`) 뒤에 좁게 통과** —
  흩뜨리지 않기. (단, Repository 를 Port 로 승격하는 건 **지금 하지 않는다.** CLAUDE.md 컨벤션대로
  "구현체 교체 여지가 실제로 관측될 때" 뽑는다 — 조기 추상화 회피.)
- **모든 메시지 조회를 sessionId 기반으로 제한** — 유일한 예외인 rate limit 의 userId 크로스-세션 집계
  (`countRecentUserMessagesByOwner`)는 그래서 **Redis 카운터로 분리**하는 방향. (Redis 는 다중 인스턴스
  확장 시 어차피 필요 — Caffeine 은 단일 인스턴스 전제.) 급하지 않고, "메시지 분리 또는 다중 인스턴스
  확장, 둘 중 먼저 오는 것" 시점에.
- **관계 데이터(`AiChatSession`/`Summary`)는 MySQL 유지.** `SummaryJob` 은 추후 외부 메시지 큐로 이관 예정.

## 높은 부하 가정 시 확장 설계 지도 (학습·대비용)

실제 착수 순서가 아니라, 벽이 다가올 때 꺼낼 카드의 순서와 각 카드가 푸는 문제를 정리한다.
**핵심 원리: 부하는 소수의 뜨거운(ACTIVE) 세션에 몰리고, 데이터 대부분은 차가운(LOCKED) 채로 쌓인다.
따라서 "뜨거운 소수를 빠르게, 차가운 다수를 싸게" 가 모든 기법의 뿌리다.**

### 조회 부하 (이 앱의 핵심 — 매 턴 컨텍스트 재조회)

| 기법 | 이 앱에서 | 효과 |
|---|---|---|
| **핫 리드 캐싱** | 활성 세션 최근 40개를 Redis capped list 로, write-through | 매 턴 DB 재조회 제거 — **가장 큰 레버** |
| **키셋 페이지네이션** | `(created_at DESC, id DESC)` 커서 — 이미 이 정렬 | 깊은 페이지 offset 저하 회피 |
| **읽기 복제본** | 콜드 리플레이·UI 히스토리를 복제본으로 | 읽기/쓰기 분리 |

### 쓰기 부하 (append 폭증)

| 기법 | 이 앱에서 | 효과 |
|---|---|---|
| **카운터 경합 제거** | `session.accumulated_tokens` 매 메시지 read-modify-write → 원자 증가/지연 집계 | 핫 로우 락 경합 해소 |
| **인입 버퍼(큐)** | 메시지를 큐에 먼저 쓰고 비동기 저장 | 쓰기 스파이크를 저장소에서 디커플링 |
| **샤딩(wide-column)** | sessionId 로 Dynamo/Scylla 분산 | 단일 프라이머리 천장 초과 |

### 저장소 카드의 착수 트리거

| 카드 | 트리거 | 푸는 문제 |
|---|---|---|
| 인스턴스 상향 | 쓰기 지연·커넥션 대기 관측 시 | 쓰기 처리량 |
| 시간 파티셔닝 | 테이블이 아직 작을 때(거대해지면 ALTER 고통) | 테이블 비대화 |
| 아카이빙(콜드 반출, `EXCHANGE PARTITION`) | 파티션된 핫 테이블조차 커질 때 | 테이블 비대화 |
| wide-column 샤딩 | 단일 노드 쓰기 천장에 실제 근접 | 쓰기 수평 확장 |

### 관측 우선 (지금 실익 있는 유일한 것)

대용량 관리는 **측정 → 병목 발견 → 개선 → 재측정** 루프로 배운다. 저장소 기계장치를 미리 짓는 대신:

- **성장 계기판**: 테이블 row 수·저장 용량 증가율·INSERT 지연을 주기 관측 (RDS `perf_schema`·slow_log 이미 켬)
- **부하 생성기(k6 등)**: 동시 채팅 스트림을 만들어야 병목을 재현·검증 가능. 이게 없으면 위 설계는 전부 가설.
