# AI 채팅 — 배포 종료 대기와 미정산 예약 반환

배포·재시작 때 진행 중이던 채팅 턴이 어떻게 마무리되는지, 마무리하지 못한 것은 누가
치우는지를 적는다. 두 장치가 나눠 맡는데 역할이 다르므로 하나가 다른 하나를 대신하지 못한다.

## 현재 구성

### 두 장치의 역할 분담

| | 종료 대기 (`AiChatShutdownLifecycle`) | 미정산 예약 반환 (`AiChatExpiredTurnScheduler`) |
|---|---|---|
| 무엇을 보는가 | JVM 메모리의 진행 목록 (`AiChatInFlightTurnRegistry`) | DB 의 미종료 요청 행 (`ai_chat_turn_request`) |
| 언제 도는가 | shutdown 신호를 받았을 때 한 번 | 상시, 60초 주기 |
| 무엇을 하는가 | 진행 중인 생성·후처리가 끝나기를 최대 60초 기다린다 | 기한 지난 미종료 행을 `EXPIRED` 로 확정하고 예약 토큰을 사용자에게 돌려준다 |
| 못 하는 것 | 프로세스가 강제로 죽으면 목록째 사라진다 | 받다 만 답변을 되살리거나 OpenAI 를 다시 부르지 않는다 |

**메모리 목록은 반환의 근거가 될 수 없다.** 프로세스와 함께 사라지기 때문이다. 반대로 DB 행만
보면 정상적으로 처리 중인 요청과 죽은 요청을 구분할 수 없어, 기한이 지나기를 기다려야 한다.
그래서 배포처럼 미리 아는 종료에서는 메모리 목록으로 기다려 주고, 예상 못 한 종료·기한 초과는
DB 행으로 정리한다.

종료 대기가 목록에서 턴을 지우는 것은 "이번 실행이 끝났다" 는 뜻이지 "업무가 성공했다" 는 뜻이
아니다. 후처리가 실패해 확정하지 못한 요청은 미종료로 남아 미정산 예약 반환 대상이 된다.

**SSE 전달의 종료는 두 장치 어느 쪽의 조건도 아니다.** 살아 있는 SSE 요청을 기다리는 일은
웹 서버의 graceful shutdown 이 따로 한다.

### 미정산 예약 반환이 고치는 것

**선불 예약(R)이 걸린 뒤 그 턴을 끝내는 코드(성공 정산 또는 실패 환불)가 영영 돌지 않으면 —
프로세스 사망, 종료 중 후처리 제출 거절, 후처리 예외 — 그 사용자의 일일 예산에서 R 이 그날 내내
묶인다.** 답변은 DB 에 없고 다른 사용자에게는 영향이 없다. 고칠 것은 이 하나다.

**스케줄러는 청구하지 않는다.** 묶인 예약을 돌려주고 요청을 닫는 것만 한다. 답변 저장과 청구는
같은 트랜잭션이라 "저장됐는데 미청구" 는 존재하지 않기 때문이다. 받다 만 답변을 되살리거나
OpenAI 를 다시 부르지도 않는다 — 사용자가 답변을 원하면 새 요청 식별자로 다시 보낸다.

그 하나를 안전하게 하려고 세 가지를 둔다.

- **기한** — 시간이 지났다는 것이 실행이 사라졌다는 증명은 아니다. 그래서 접수 시각에 한 턴이
  정상적으로 끝나기까지 걸릴 수 있는 구간을 다 더한 `expires_at` 을 찍어 두고, 그보다 오래된
  미종료 행만 대상으로 삼는다.
- **행 잠금** — 확정하는 순간 요청 행을 잠그고 미종료·기한 초과를 다시 확인한다
  (`AiChatTurnOutcomeWriter#expireIfOverdue`). 늦게 성공한 실행과 반환이 같은 행에서 만나도
  한쪽만 반영된다. 정확성을 보장하는 것은 시간 여유가 아니라 이 잠금이라, 별도의 분산 잠금도
  선점 표식도 두지 않았고 유예(`grace-seconds`)도 0 이다.
- **묶음** — 한 번에 읽어 오는 행 수를 묶어 한 묶음이 만드는 순간 부하를 제한한다. 묶음이 꽉 차면
  같은 스캔이 곧바로 다음 묶음을 읽어, 밀린 양이 많아도 한 스캔에서 비운다.

### 종료 순서

> 신규 수락 차단 → 진행 목록이 비거나 기한(60초)이 될 때까지 대기 → 실행기 두 개 종료
> → (빈 소멸) DB 커넥션 풀·HTTP 클라이언트 종료

- **신규 수락 차단**: 차단과 진행 목록 등록이 같은 잠금을 쓴다. 서로 다른 잠금을 쓰면
  "차단 플래그를 보기 전에 등록이 시작됐지만 아직 목록에 들어가지 않은" 순간이 생겨,
  수락해 놓고 종료 대기에서는 빠뜨리는 턴이 나온다. 차단된 뒤 도착한 요청은 503 으로 거절한다.
- **대기**: 최대 유예 시간이지 무조건 그만큼 사는 설정이 아니다. 목록이 비면 곧바로 다음 단계다.
- **실행기 종료**: 전달·후처리 가상 스레드 실행기 두 개는 이 종료 절차가 직접 닫는다.
- **DB 풀·HTTP 클라이언트**: 빈 소멸 때 닫히고, 빈 소멸은 모든 SmartLifecycle 종료가 끝난
  **다음**이다. 그래서 후처리가 DB 를 쓰는 동안 풀이 먼저 닫히지는 않는다. 단, 단계별 기한을
  넘겨 lifecycle 이 우리를 두고 먼저 진행한 경우에는 이 보장이 사라진다 — 그때 실패한 후처리는
  DB 의 미종료 예약으로 남아 다음 스캔이 돌려준다.

### 왜 웹 서버 graceful shutdown 과 같은 단계(phase)인가

"웹 서버와 같은 단계면 안전하다" 가 아니라, **이 서버의 실제 종료 유예 시간에 들어맞는 배치가
이것뿐**이라서다. 관련 값은 이렇다.

| 값 | 어디에 있는가 |
|---|---|
| `server.shutdown: graceful`, `spring.lifecycle.timeout-per-shutdown-phase: 60s` | `application.yml` |
| ai-chat 종료 대기 상한 60초 | `application.yml` 의 `ai-chat.streaming.shutdown-wait-seconds` |
| `TimeoutStopSec=75` (그 뒤 SIGKILL) | `infra/systemd/readum-*.service` |
| 웹 서버 graceful shutdown 단계 = `Integer.MAX_VALUE - 1024` | spring-boot-web-server 4.0.5 |

같은 단계의 빈들에게는 먼저 모두 stop 을 걸고 나서 하나의 latch 를 단계별 기한만큼 기다린다
(spring-context 7.0.6). 즉 **같은 단계면 두 대기가 겹쳐 흘러 최대 60초**에 들어온다. 우리 대기를
낮은 단계에 두면 HTTP 대기(최대 60초)가 **끝난 뒤에** 우리 대기(최대 60초)가 시작돼 합이 최대 120초가
되고, 75초에 SIGKILL 이 떨어져 둘 다 잘린다. 기한을 내린(전달 30초, `emitter` 40초) 뒤에도 SSE 는
채팅에서 가장 긴 요청이라 HTTP 대기가 40초 가까이 쓰일 수 있고, 거기에 우리 대기 60초가 이어 붙으면
100초로 여전히 75초를 넘는다. 즉 두 대기를 겹쳐 흘려야 한다는 결론은 새 값에서도 그대로다.

**남은 위험(측정·조정 대상):** 종료 대기 상한(60초)이 단계별 기한(60초)과 같다. 두 시계가 같은 순간에
만료되면 lifecycle 쪽에 "기한 내 종료 실패" 경고가 남을 수 있다. 다만 생성 전체 기한을 20초로 내린
뒤에는 **정상 턴이 종료 대기 안에 끝난다** — 생성 20초 + 후처리(보통 1초 안)라 60초를 채울 수 없다.
남은 경우는 후처리가 DB 쪽 대기 제한(연결 획득 10초 · 잠금 대기 5초)까지 끌려가는 이례적인 상황뿐이다.
값 조정(종료 대기 < 단계별 기한)은 아직 하지 않았다 — 재측정에서 이 상황이 재현되지 않아
(진행 중 50건이 2.19초에 정리) 조정 근거가 생기지 않았고, 위험 자체는 그대로 남아 있다.

### 부하 재측정 결과 (2026-09-06)

로컬 mock 환경에서 이 문서가 설명하는 종료·반환 동작을 실제로 확인했다.

- **정상 종료(SIGTERM)**: 진행 중 50건이 **2.19초**에 정리됐고, 로그와 자원 종료 순서가 위 설명대로였다
  (신규 턴 수락 차단 → 진행 턴 정리 → 실행기 종료 → DB 풀 종료). 50건 전부 DB `SUCCEEDED`, 미종료 잔류 0.
  Tomcat 종료가 턴 정리보다 먼저 끝난 실행도 있어, **SSE 전달 종료가 완료 조건이 아니라는 점**이 실물로 확인됐다.
- **강제 종료(kill -9)**: 진행 중 50건이 `RESERVED`(예약 26,300 토큰)로 남았고, 재기동 뒤 반환 스캔 한 번에
  50건 `EXPIRED` · 26,300 반환 · 사용자 예산 총합이 부하 전 값으로 정확히 복귀했다.
- 같은 재측정에서 부하 N=50·100 각 2라운드가 모두 성공률 100%(HTTP + SSE + DB 3조건)였다.

상세와 한계는 미추적 디렉터리의 보고서에 있다 —
`load-test/campaigns/2026-09-06_stage2-generation-delivery-split/results/reports/2026-09-06-condC-result.md`.

### 설정 항목

`application.yml` 의 두 묶음이다. **아래 값은 모두 후보값이다.** 기한 셋(생성 전체·무응답·전달)은
2026-09-06 에 "실제 생성은 길어야 10~15초" 라는 사용자 판단에 맞춰 내렸다. 그 판단은 아직 실측이 아니다 —
감사 로그에서 생성 소요 분포를 뽑아 확인하는 것이 다음 일이고, 그 결과로 다시 조정한다.

`ai-chat.streaming` — 한 턴의 기한과 전달 버퍼:

| 키 | 현재 값 | 무엇을 언제부터 재는가 |
|---|---|---|
| `generation-total-timeout-seconds` | 20 | 생성 전체 기한. 외부 API 호출 시작부터, 청크가 계속 와도 적용하는 절대 상한. **자원 보호 상한** — 관측 최대 15초(사용자 판단)에 여유 3분의 1. 걸리면 생성을 끊고 본문을 버리며 예약을 되돌린다(OpenAI 과금은 남는다) |
| `generation-idle-timeout-seconds` | 10 | 무응답 기한. 스트림 시작, 그 뒤로는 청크 1건을 받을 때마다 다시 시작. **사용자가 느끼는 값** — 첫 토큰 대기와 중간 멈춤을 여기서 잡는다 |
| `delivery-timeout-seconds` | 30 | 전달 기한. 전달 채널을 만든 시점(선행 처리 통과 직후, `SseEmitter` 를 돌려주기 직전)부터. 생성 전체 기한 + 10초 — 완성본 교체까지 담아야 해서 생성 전체 기한보다 길다 |
| `shutdown-wait-seconds` | 60 | 종료 대기 상한. shutdown 신호부터 |
| `prepare-allowance-seconds` | 10 | 기한이 아니라 **여유**. 요청 만료 시각 산식에만 쓴다 |
| `post-processing-allowance-seconds` | 20 | 마찬가지로 **여유** |
| `delivery-queue-capacity` | 256 | 연결 1개당 전달 큐에 쌓아둘 델타 개수 |

`ai-chat.turn-recovery` — 미정산 예약 반환:

| 키 | 현재 값 | 뜻 |
|---|---|---|
| `scan-interval-ms` | 60000 | 스캔 주기. 컨텍스트 요약 회수기와 같은 간격 |
| `grace-seconds` | 0 | `expires_at` 을 넘긴 행을 곧바로 처리한다 |
| `max-rows-per-run` | 100 | 한 번에 읽어 오는 행 수(묶음 크기). 상한이 아니다 |

**만료 시각 산식**은 이렇다.

```
expires_at = 접수 시각 + (선행 여유 10 + 생성 전체 기한 20 + 후처리 여유 20) = 50초
```

**한 턴의 시간 예산이 50초**라는 뜻이다 — 접수부터 그 안에 끝나거나 어느 구간에서든 명시적으로
실패한다. 늦게 성공하는 대신 빨리 실패하는 쪽을 택했다. 이 선을 덮지 못하면 정상 처리 중인 요청을
반환이 가로채 환불하므로, 각 몫은 그 구간의 실제 상한에서 온다.

- **선행 여유 10초** — 가장 긴 몫은 입력 moderation 의 HTTP 상한 8초(연결 3 + 읽기 5,
  `OpenAiHttpClientConfig`). 그 뒤로 이력 조회·예약·전역 게이트·USER 저장의 DB·Redis 시간이
  더 붙어 2초를 얹었다.
- **후처리 여유 20초** — DB 연결을 빌리는 데 Hikari `connection-timeout` 10초가 들 수 있고,
  그 뒤 트랜잭션 안에서 같은 요청 행을 잠그는 대기가 `innodb_lock_wait_timeout` 5초까지 갈 수 있다.
  연결 획득 10초에 저장·정산 몫 10초를 얹었다.
- **유예 0초** — 유예를 늘려도 정확해지지 않는다. 정확성은 행 잠금이 보장하고, 유예는 예약이
  사용자에게 돌아가는 시각만 늦춘다. 0 이 아닌 값은 요청 행의 시각과 스캔이 읽는 시각의 출처가
  다른 환경(인스턴스 간 시계 차이)에서만 의미가 있다.

**구간별 상한이 이 예산 안에 드는지는 기동 시 대조한다.** `AiChatTimeBudgetValidator` 가
무응답 ≤ 생성 전체, 전달 > 생성 전체, moderation 연결+읽기 < 선행 여유, Hikari 연결 획득 < 후처리 여유
네 가지를 보고 어긋나면 기동을 막는다. 값들이 서로 다른 파일에 흩어져 있어, 한 곳만 바꿨을 때
"정상으로 끝날 수 있는 최장 시간 > 만료" 가 조용히 생기는 것을 막는 자리다.

**여기 적은 초 단위는 설정값과 라이브러리 기본값에서 읽은 계산이지 측정값이 아니다.** 실제 선행
처리·후처리 소요는 아직 재지 않았다. 종료 대기 상한(60초)은 이 산식에 들어가지 않는다 — 배포 때
얼마나 기다려 줄지를 정하는 값이지 한 턴이 얼마나 걸리는지가 아니다.

**반환이 늦어지는 정도:** 죽은 요청의 예약이 사용자에게 돌아오기까지 최악
`expires_at + 스캔 주기` = 접수 후 약 1분 50초다. 그 사이 사용자는 그만큼의 일일 예산을 못 쓴다.
스캔 한 번이 밀린 양을 다 비우므로, 이 지연은 밀린 양이 많아도 늘어나지 않는다.

### DB 연결의 대기 제한

후처리에는 전체 타이머가 없다. 무한정 매달리는 일을 막는 몫은 DB 쪽 대기 제한에 있는데,
이 셋은 서로 다른 구간을 잰다.

| 제한 | 값 | 무엇을 재는가 |
|---|---|---|
| `spring.datasource.hikari.connection-timeout` | **10초** (`application-{local,dev,prod}.yml`) | 풀에서 연결 하나를 **빌리기까지** 기다리는 시간 |
| JDBC `socketTimeout` | **60초** (`application-{local,dev,prod}.yml` 의 URL 매개변수) | 빌린 연결에서 **응답 한 덩어리를 읽기까지** 기다리는 시간 |
| `innodb_lock_wait_timeout` | **5초** (같은 파일들의 Hikari `connection-init-sql`) | 서버가 행 잠금을 **얻기까지** 기다리는 시간 |

셋 다 앱 전체에 걸리고, 셋 다 앱에서 못박는다 — DB 서버 파라미터에 기대지 않으므로 로컬 컨테이너와
RDS 어디서든 같은 값이 보장된다.

**`socketTimeout` 이 막는 것.** 이 값이 없으면 읽기에 기한이 없다. 소켓이 조용히 끊기면
(네트워크 장비가 유휴 연결을 정리하거나, 상대가 알리지 않고 사라지는 경우) 클라이언트는 오지 않을
응답을 커널 keepalive 시간(리눅스 기본 약 2시간)까지 기다린다. 그동안 그 호출을 하던 스레드도,
그 스레드가 쥔 풀 연결도 회수되지 않는다. 채팅 후처리에서 드러난 문제지만 원인은 DataSource 한
군데라, 앱의 모든 DB 호출에 같은 값을 건다.

**왜 60초인가.** MySQL 의 잠금 대기 기한(기본 50초)보다 길어야 한다. 잠금 대기가 길어졌을 때
클라이언트가 먼저 소켓을 끊으면 서버 세션은 잠금을 쥔 채로 남을 수 있다. 읽기 기한을 잠금 대기
기한보다 길게 두면 그 경우가 DB 쪽에서 정상 오류(`Lock wait timeout exceeded`)로 먼저 끝나고
트랜잭션이 롤백된다. 앱의 질의는 모두 짧아 정상 처리가 60초를 넘길 여지가 없고, 60초는 널리 쓰는
보편값이다. **이 값은 계산이지 측정이 아니다** — 실제 질의 소요는 재지 않았다.

**왜 연결 획득 10초인가.** 기본값은 30초다. 풀이 10초 넘게 비어 있는 상황은 어느 기능에서든
정상이 아니다 — 그만큼 기다려 얻은 연결로 일을 시작해 봐야 그 요청은 이미 늦었다. 채팅에서는
후처리 여유 20초(= 연결 획득 10 + 저장·정산 10)가 성립하려면 이 값이 그 안에 들어야 한다.
읽기 기한이 이 구간을 대신할 수 없다 — "풀에서 빌리기" 와 "빌린 연결에서 읽기" 는 다른 구간이다.

**왜 잠금 대기 5초인가.** 한 트랜잭션이 다른 트랜잭션이 쥔 행 잠금을 기다리는 최대 시간이고,
넘으면 그 문장이 오류로 끝나 트랜잭션이 롤백된다(JPA 예외 → Spring 롤백). 기본 50초는 후처리
여유 20초 안에 들지 않는다. 채팅에서는 요청 행을 `FOR UPDATE` 로 잠그는 후처리와 미정산 예약
반환이 같은 행에서 만나는 순간에, 그 밖의 기능(감상문 잡 적재 등)에서는 각자의 잠금 경합에 걸린다.
`socketTimeout` 60초가 이 값보다 길어, 잠금 대기는 **항상 DB 쪽에서 먼저** 정상 오류
(`Lock wait timeout exceeded`)로 끝난다 — 클라이언트가 먼저 소켓을 끊어 서버 세션이 잠금을 쥔 채
남는 경우가 없다. 이 설정으로 이슈 #92(summary_job 적재 락 대기)의 후속 항목
"`lock_wait_timeout` 단축" 이 닫힌다.

테스트 프로파일(H2)에는 둘 다 걸지 않는다. `socketTimeout` 은 H2 가 모르는 연결 설정이라 거부하고
(`Unsupported connection setting "SOCKETTIMEOUT"`), 인메모리라 기다릴 소켓 자체가 없다.
연결 초기화 SQL 도 H2 가 문법 오류로 거부한다
(2.4.240 에서 `Syntax error in SQL statement "SET SESSION [*]innodb_lock_wait_timeout = 5"` 확인).
실제로 걸렸는지는 `./gradlew mysqlTest` 가 확인한다 — `DataSourceSocketTimeoutMySqlTest` 는 풀에서
빌린 연결의 `Connection#getNetworkTimeout()` 이 60,000ms 인지(Connector/J 는 `socketTimeout` 을 이 값으로
노출한다), `DataSourceLockWaitTimeoutMySqlTest` 는 같은 연결의 `@@innodb_lock_wait_timeout` 이 5 인지
단언한다. 둘 다 값을 베끼지 않고 `application-local.yml` 에서 읽어 온다.

### 수동 실행 전용 테스트 — `./gradlew mysqlTest`

기본 빌드(`./gradlew test`, `./gradlew build`)의 테스트는 H2(MODE=MySQL)로 돈다. H2 는 MySQL 의
잠금·유일성 의미를 그대로 재현하지 않으므로, **DB 경쟁에 기대는 계약은 실제 MySQL 로 따로
확인한다.** `mysql` 태그가 붙은 테스트가 그것이고 기본 빌드에서는 제외된다.

지금 확인하는 것: 같은 `requestId` 동시 삽입에서 정확히 한 건만 통과하는가
(`AiChatTurnRequestMySqlUniquenessTest`), 요청 종료가 같은 행을 잠가 늦은 성공과 미정산 예약 반환이
서로를 밀어내는가(`AiChatTurnOutcomeMySqlRowLockTest`), 프로파일에 적은 두 대기 제한이 풀에서 빌린
연결에 실제로 걸리는가(`DataSourceSocketTimeoutMySqlTest` · `DataSourceLockWaitTimeoutMySqlTest`).

전제와 실행:

```bash
# 로컬 MySQL 컨테이너 (readum-local-mysql, 127.0.0.1:3307) 가 떠 있어야 한다
MYSQL_TEST_PASSWORD=... ./gradlew mysqlTest
```

접속 정보는 환경 변수로 덮어쓸 수 있다 (`MYSQL_TEST_HOST` / `PORT` / `DATABASE` / `USER` /
`PASSWORD`, 비밀번호는 `MYSQL_PASSWORD` 도 인식). 이 테스트는 마이그레이션 파일로 임시 테이블을
만들고 끝나면 지운다 — 운영 테이블을 건드리지 않는다.

## 변경 절차와 주의점

- **종료 대기 상한과 `spring.lifecycle.timeout-per-shutdown-phase`, `TimeoutStopSec` 은 함께
  본다.** 하나만 올리면 systemd 가 먼저 SIGKILL 을 보내 대기가 통째로 잘린다. 지금 관계는
  `종료 대기(60) ≤ 단계별 기한(60) < TimeoutStopSec(75)` 이다.
- **`ai-chat.streaming` 의 기한을 바꾸면 만료 시각도 함께 움직인다.** 생성 전체 기한을 늘리면
  `expires_at` 도 그만큼 늘어난다(산식에 들어 있다). 반대로 여유를 줄일 때는 그 구간의 실제 상한
  (moderation HTTP · Hikari 연결 획득)이 여전히 그 안에 드는지 본다 — 어긋나면 기동이 막힌다.
- **구간별 상한을 줄일 때는 여유도 함께 본다.** moderation HTTP 상한은
  `OpenAiHttpClientConfig`, DB 대기 제한은 `application-{local,dev,prod}.yml` 의 Hikari 블록에 있다.
  둘 다 채팅 밖의 기능에도 걸리는 값이므로, 채팅 예산만 보고 줄이지 않는다.
- **전달 기한을 늘릴 때는 `emitter` 기한이 거기서 파생된다는 것을 기억한다**(전달 기한 + 10초).
  `emitter` 가 먼저 만료되면 컨테이너가 요청을 끊어 전달 기한이 상한 구실을 못 하고, 가장 늦게
  도착하는 이벤트인 완성본 교체(`replace`)가 잘린다.
- **반환 스케줄러는 여러 대가 동시에 돌아도 안전하다.** 반환은 행 잠금과 미종료 확인 덕분에
  한 번만 반영된다. 별도의 분산 잠금이나 선점 표식을 두지 않은 이유이므로, 배포 대수를 늘릴 때
  이 스케줄러를 끄거나 한 대에만 남길 필요가 없다. 한 프로세스 안에서 스캔이 겹치지 않는 것은
  `@Scheduled(fixedDelay)` 가 이전 실행이 끝난 뒤부터 간격을 재기 때문이다.
- **반환 로그는 만료가 실제로 있었을 때만 남는다**(`WARN`). 평소 조용한 것이 정상이고, 이 로그가
  꾸준히 찍힌다면 기한·여유 값이 실제 소요보다 짧다는 신호일 수 있다. 로그의 `묶음=` 이 1 보다 크면
  한 주기에 한 묶음(100건)을 넘는 양이 밀렸다는 뜻이다.
