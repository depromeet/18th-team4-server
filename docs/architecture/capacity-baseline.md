# AI 기능 용량 기준 (capacity baseline)

AI 기능(채팅·감상문·중간 요약·제목 생성)의 정책값 — 토큰 예약량, 기능별 분당 토큰 몫,
부하 시나리오 — 이 어떤 가정과 계산에서 나왔는지를 한곳에 모은 근거 문서다.
자원 배분(#167)과 토큰 원장(#164) 작업은 이 문서의 값을 출발점으로 쓰고,
값을 바꿀 때는 이 문서를 함께 고친다.

**값의 출처 표기 규칙** — 모든 수치는 셋 중 하나로 표기한다.

- `[사실]` — 코드·설정·계정에서 확인한 값
- `[로컬 계산]` — 실제 도구를 돌려 얻은 값 (운영 데이터 아님)
- `[가정]` — 실데이터 없이 정한 추정값. 운영 데이터가 생기면 교체 대상

> 운영 실측 데이터는 없다. 런칭(2026-06-20) 이력은 있으나 현재 운영 중단 상태이고
> 당시 DB 는 삭제되었다. 사용자 행동 수치는 전부 `[가정]` 이다.

## 사용자 행동 가정 [가정]

성장 시나리오의 목표 규모다. 현재 규모가 아니며, 아래 도출값은 전부 이 값들에
비례하므로 규모가 다르면 비례 환산하면 된다.

| 항목 | 값 | 근거 |
|------|----|------|
| 일간 활성 사용자 | 10,000명 | 성장 목표 규모 |
| 하루에 채팅 세션을 진행하는 비율 | 20% → 2,000세션/일 | 독서 기록은 매일 하는 활동이 아님 |
| 세션당 사용자 메시지 | 15건 → 30,000건/일 | 감상문에 이르는 이상적 대화 길이 |
| 메시지 평균 길이 | 100자 ≈ 70토큰 | 짧은 감상 위주 대화 |
| 감상문 생성 | 세션의 60% → 1,200건/일 | 대화를 끝까지 마친 세션 비율 |
| 중간 요약 | 세션당 2회 → 4,000건/일 | 컨텍스트 압축 주기에서 유도 |
| 제목 생성 | 세션당 1회 → 2,000건/일 | 세션당 1개 |
| 피크 집중률 | 저녁 1시간에 하루 물량의 10% | 퇴근 후 저녁 시간대 집중. 피크 분당 = 일량 × 10% ÷ 60 ≈ 일량의 0.17% |

## 호출당 토큰 기준값

입력은 `[가정]`(대표 대화 구성 × 환산율 0.7), 출력은 프롬프트로 유도하는 목표 길이와
예약에 쓰는 출력 예약값을 함께 둔다.

| 기능 | 입력 토큰 | 출력 목표 | 출력 예약값 |
|------|------|------|------|
| 채팅 응답 | 2,000 (시스템 프롬프트 + 누적 요약 + 최근 원문 + 새 메시지) | 300 | 600 |
| 감상문 생성 | 3,000 (누적 요약 + 대화 꼬리 전체) | 700 | 1,200 |
| 중간 요약 | 1,500 (직전 요약 + 신규 구간 원문) | 400 | 600 |
| 제목 생성 | 500 | 30 | 100 |

- **기본은 실사용 사후 정산이다.** 확정 차감은 응답의 usage 가 알려주는 실제 토큰으로
  한다. API 의 max_tokens 는 걸지 않는다 — 응답을 중간에 자르는 하드 스톱이라 정보가
  유실된다 (application.yml 주석·컨텍스트 압축 스펙 8절의 기존 결정 유지).
- **출력 예약값**은 자체 사용자 원장을 운영하기 때문에 필요한 예약 계층의 추정치다.
  호출 전에는 출력 크기를 알 수 없으므로 이 값으로 예약을 잡는다:
  예약 = 입력(요청 시점 실계산) + 출력 예약값.
- **예약값은 상한이 아니다.** 실사용이 예약값을 넘을 수 있고, 예약만으로 잔액
  불변식이 보장되지 않는다. 초과분의 정산 처리와 불변식 정의(무엇을 0으로 보장하고
  무엇을 수렴으로 보장하는지)는 원장 설계(#164) 관할.

## 피크 부하 도출

계산식: 기능별 피크 RPM = 일간 건수 × 0.17% / TPM 기여 = RPM × (입력 + 출력 목표).

**보통 시나리오** (위 가정 그대로):

| 기능 | 피크 RPM | 피크 TPM 기여 |
|------|------|------|
| 채팅 응답 | 50 | 115,000 |
| 감상문 생성 | 2 | 7,400 |
| 중간 요약 | 6.7 | 12,700 |
| 제목 생성 | 3.3 | 1,800 |
| **합계** | **62** | **≈ 136,900 (한도의 76%)** |

| 시나리오 | 배수 | 합계 TPM | 상태 |
|------|------|------|------|
| 보통 | ×1 | ≈ 137,000 (76%) | 한도 내. 배분 없이도 동작 |
| 높음 | ×2 | ≈ 274,000 (152%) | 한도 초과. 게이트가 개입, 채팅 몫 보호 필요 |
| 극단 | ×5 | ≈ 685,000 (380%) | 비동기 전면 대기열화, 채팅도 몫 안에서 제한 |

- **TPM 이 첫 병목이다.** RPM 은 극단 시나리오(310 RPM)에서도 한도(9,000)의 3.4%에
  불과하다. 기능별 몫 배분(#167)이 필요한 근거가 여기 있다 — 높음 이상에서 비동기
  작업이 한도를 잠식하면 채팅 응답이 밀린다.
- 채팅 입력 2,000토큰 `[가정]` 이 지배 변수다 (합계의 84%가 채팅). 컨텍스트 압축
  정책이 이 값을 정하므로, 압축 경계가 바뀌면 이 표를 다시 계산한다.

## 정책 초기값

| 정책 | 초기값 | 근거 |
|------|------|------|
| 기능별 TPM 몫 | 채팅 70% (126,000) / 비동기 합산 30% (54,000) | 보통 피크에서 채팅 115,000 < 126,000, 비동기 22,000 < 54,000. 세부 배분·조정은 #167 에서 |
| 토큰 예약량 | 입력(요청 시점 실계산) + 출력 예약값 | 위 표. 원장 설계는 #164 |
| 입력 한도 | 현행 유지 (채팅 4,000자 등) | 상한 초과 시나리오는 게이트·예약이 방어 |

## 채팅 진행 중 턴 상한

`ai-chat.streaming.max-in-flight-turns` = **300** (2026-09-06, **계산값·임시값**).
이 프로세스가 동시에 진행할 수 있는 채팅 턴 수의 상한이다. 한 턴은 선행 처리 시작부터 마지막
후처리까지를 말한다(`AiChatInFlightTurnRegistry` 의 추적 구간). 넘으면 503 `AI_CHAT_CAPACITY_EXCEEDED`.

**무엇을 막는 값인가.** 평소 유입을 조절하는 것은 사용자별 폭주 가드(`UserMessageRateLimiterRedisAdapter`)와
전역 게이트(`OpenAiRequestGate`)인데, 둘 다 Redis 에 기대고 Redis 가 죽으면 검사 없이 통과시킨다
(fail-open, [record 0006](../record/0006-openai-rate-limit-defense-flow.md)). 그 순간 앱이 받는 만큼 다 받아
자기 자원을 먼저 소진하는 것을 막는 **마지막 안전장치**다. 처리량 목표가 아니고, Redis 고가용성을 대신하지도 않는다.

아래는 세 자원의 상한을 각각 계산하고 그 최솟값에 여유를 뺀 과정이다. **모든 값이 계산이고 실측이 아니다.**

### 1. 힙

| 입력값 | 값 | 출처 |
|---|---|---|
| 배포 JVM 힙 상한 | 256MB | `[사실]` `infra/systemd/readum-*.service` 의 `-Xmx256m` |
| 기준 사용량(요청 없이 떠 있을 때의 살아 있는 객체) | 128MB (= 힙의 절반) | `[가정]` 아래 설명 |
| 모델 최대 출력 토큰 | 16,384 | `[확인 필요]` gpt-4o-mini 의 공식 최대 출력 토큰. 저장소 안에서 확인할 근거가 없어 모델 문서 값을 그대로 썼다 |
| 토큰당 문자 수 | 1 ÷ 0.614 ≈ 1.63자 | `[로컬 계산]` 위 "한글 토큰 환산율" 종합값의 역수 |

**기준 사용량을 힙의 절반으로 둔 이유.** 이 값의 실측이 없다. 부하 캠페인의 스냅숏
(`load-test/campaigns/2026-09-06_stage2-generation-delivery-split/results/metrics/heap-condC-after-rounds.txt`,
사용 중 184MB)은 참고가 되지 않는다 — 젊은 세대의 쓰레기가 섞여 있고, 힙 4.5GB 환경이라 수집 시점이
배포 환경과 전혀 다르다. 실측이 없을 때 기준 사용량을 낮게 잡으면 상한이 높게 나오므로, 틀렸을 때 안전한
쪽인 절반으로 둔다. 실측이 생기면 여기부터 고친다.

턴 하나가 힙에 들고 있을 수 있는 최대치. 최대 답변 길이 = 16,384토큰 × 1.63자 ≈ **26,700자**.

| 항목 | 식 | 값 |
|---|---|---|
| 누적 본문(`StringBuilder`, 확장 여유 2배) | 26,700자 × 2B × 2 | 104 KB |
| 전달 큐 | 256개 × (델타 8자 × 2B + 객체 오버헤드 64B) | 20 KB |
| 저장 단계의 본문 복사본 1개 | 26,700자 × 2B | 52 KB |
| SSE 직렬화 버퍼(완성본 교체 1건, 한글 UTF-8 3B/자) | 26,700자 × 3B | 78 KB |
| 가상 스레드 2개(전달·후처리)의 스택 | 2 × 16 KB | 32 KB |
| **합계** | | **286 KB → 올림 320 KB** |

> 전달 큐 256개는 `delivery-queue-capacity` `[사실]`, 델타 8자와 객체 오버헤드 64B 는 `[가정]` 이다.
> 가상 스레드 스택은 고정 크기가 아니라 필요한 만큼 늘어난다 — 16KB 는 짧은 호출 스택의 어림값 `[가정]`.

**힙 상한 = (256MB − 128MB) ÷ 320KB = 131,072KB ÷ 320KB ≈ 409턴.**

### 2. OpenAI 스트리밍 연결 풀 (reactor-netty)

`OpenAiConfig#streamingChatModel` 이 쓰는 WebClient 의 연결 풀이다. 기본값을 실제로 확인했다
(`javap -c`, gradle 캐시의 `reactor-netty-core-1.3.4.jar` · `reactor-netty-http-1.3.4.jar` — 실행 시점의 버전이다).

| 값 | 확인 결과 | 확인한 곳 |
|---|---|---|
| `ConnectionProvider.DEFAULT_POOL_MAX_CONNECTIONS` | `max(availableProcessors, 8) × 2` → 2 vCPU(t3.small)에서 **16** | `ConnectionProvider` 정적 초기화 |
| `DEFAULT_POOL_ACQUIRE_TIMEOUT` | **45,000ms** | 같은 곳 |
| `pendingAcquireMaxCount` 미지정 시 | **2 × maxConnections** | `PooledConnectionProvider$PoolFactory` 생성자 |
| **WebClient 기본 연결이 실제로 쓰는 풀** | 전역 공유 풀 `HttpResources`, 최대 연결 **`max(DEFAULT_POOL_MAX_CONNECTIONS, 500)` = 500** | `TcpResources#getOrCreate` |

**정정:** "최대 연결 = `max(CPU, 8) × 2`" 는 `ConnectionProvider.create(name)` 계열의 기본값이고,
`WebClient.builder()` 의 기본 연결이 타는 전역 공유 풀은 거기에 500 의 하한을 덧씌운다.
즉 손대지 않은 상태의 실제 값은 **최대 연결 500 · 대기 큐 1,000 · 대기 기한 45초**다.

그래서 이 풀은 지금 제약이 아니다(500 > 힙 상한 409). 그래도 전용 풀을 준다. 이유는 두 가지다.

1. 전역 공유 풀은 이 앱의 다른 WebClient 사용자와 자리를 나눠 쓰는 자원이라, 채팅 스트림의 동시성이
   거기 섞이면 어느 쪽이 어느 쪽을 밀어냈는지 볼 수 없다.
2. 초과가 45초짜리 대기로 조용히 쌓이는 것보다, 우리 상한이 503 으로 빨리 거절하는 편이 낫다.
   풀 대기는 그 뒤의 보조여야 한다.

전용 풀(`OpenAiConfig#openAiStreamingConnectionProvider`, 이름 `openai-streaming`)의 값은 상한에서 파생한다 —
최대 연결 = 상한(300), 대기 큐 = 상한의 1/4(75), 대기 기한 = 5초. 정본은 `max-in-flight-turns` 한 곳이라
둘이 어긋날 수 없다.

### 3. 정상 운영에서 게이트가 허용하는 진행 중 턴 수

상한이 정상 운영을 방해하지 않는지 확인하는 계산이다. 이 값은 상한의 천장이 아니라 **밑에서 밀어 올리는 조건**이다 —
상한이 이 범위보다 작으면 Redis 가 멀쩡할 때도 거절이 난다.

| 입력값 | 값 | 출처 |
|---|---|---|
| 전역 게이트 분당 토큰 예산 | 180,000 | `[사실]` `application.yml` `openai-gate.models.gpt-4o-mini.tokens-per-minute` |
| 시스템 프롬프트 | ≈ 1,000토큰 | `[로컬 계산]` `prompts/reading-assistant-system.st` 1,599자 × 0.614 |
| 이력 최대 | 8,000토큰 | `[사실]` `ai-chat.context.assembly-recent-raw-max-tokens` |
| 출력 추정 | 512토큰 | `[사실]` `ai-chat.token-budget.estimated-output-tokens` |
| 생성 전체 기한 | 120초 = 2분 | `[사실]` `ai-chat.streaming.generation-total-timeout-seconds` |

- 턴당 계상이 가장 클 때: 1,000 + 8,000 + 512 = 9,512 → 180,000 ÷ 9,512 ≈ **18.9턴/분** → × 2분 = **38턴**
- 턴당 계상이 가장 작을 때(이력 없음, 100자 메시지 ≈ 70토큰): 1,000 + 70 + 512 = 1,582 →
  180,000 ÷ 1,582 ≈ **113.8턴/분** → × 2분 = **228턴**
- 현실적인 값(위 "호출당 토큰 기준값" 의 채팅 입력 2,000 + 출력 예약 600 = 2,600):
  180,000 ÷ 2,600 ≈ 69턴/분 → **138턴**

즉 정상 운영의 동시 진행 턴 수는 **38 ~ 228턴** 범위이고 현실적인 값은 138턴 언저리다.
120초를 곱한 것은 보수적인 계산이다 — 실제 턴은 그보다 훨씬 빨리 끝나므로 실제 동시 수는 이보다 작다.

### 4. DB 커넥션 풀은 상한을 정하는 자원이 아니다

후처리가 저장·정산 트랜잭션 동안만 짧게 빌리고 느린 LLM 호출은 트랜잭션 밖이라, 이 풀은 동시 턴 수의
천장을 정하지 않는다(운영 24, 로컬 10). 캠페인 보고서
(`load-test/campaigns/2026-09-06_stage2-generation-delivery-split/results/reports/2026-09-06-condC-result.md`)의
N=100 실측에서 후처리 가상 스레드 98개 중 89개가 `HikariPool.getConnection` 에서 기다렸지만 전부 성공했고,
오버헤드는 0.4~0.6초였다. 다만 같은 보고서가 이것을 "이번 측정의 가장 뚜렷한 내부 병목" 이라고 적고
"얼마까지 견딘다 는 근거가 아니다" 라고 못 박고 있다 — 여기서 천장을 읽지 않는다는 뜻이지,
여유가 증명됐다는 뜻이 아니다.

### 5. 결정

| 자원 | 상한 |
|---|---|
| 힙 | 409턴 |
| 스트리밍 연결 풀 | 상한에서 파생(제약 아님) |
| 게이트 | 상한이 아니라 하한 요구 — 228턴보다 커야 정상 운영에서 거절이 없다 |

최솟값은 힙의 409턴이다. 여기서 여유 25%를 빼면 307턴이고, 읽기 쉬운 값으로 **300턴**으로 정한다.
300 > 228 이므로 게이트 범위의 상단(가장 짧은 프롬프트만 들어오는 비현실적인 가정)에서도 이 상한이
먼저 거절하지 않는다.

조건 C 실측(N=100, 로컬, 모의 서버, 성공률 100%)은 **"이 값 이하에서 구조가 버틴다" 의 하한 근거로만**
인용한다. 환경(모의 서버, 로컬 힙 4.5GB, 로컬 DB 풀 10)이 배포와 달라 상한의 근거로 쓸 수 없다.

**조정 절차.** 두 지표를 본다.

| 지표 | 뜻 |
|---|---|
| `ai_chat_in_flight_turns` | 지금 진행 중인 턴 수 (게이지) |
| `ai_chat_in_flight_rejections_total` | 상한에 걸려 거절한 누적 횟수 (카운터) |

최고치가 상한에 한참 못 미치고 거절이 0 이면 상한이 여유롭다는 뜻이고, 거절이 꾸준히 찍히면 상한이
실제 유입보다 낮거나 턴이 제때 끝나지 않는다는 신호다. 후자라면 상한을 올리기 전에 **위 힙 계산의
기준 사용량을 실측으로 바꾸는 것이 먼저다** — 상한을 힙 여유 이상으로 올리면 거절 대신 OOM 이 온다.

  틀리면 TPM 도출값도 2배 틀린다 — 그래서 하나의 숫자가 아니라 보통·높음·극단
  3개 시나리오로 검증한다.
