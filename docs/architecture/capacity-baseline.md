# AI 기능 용량 기준 (capacity baseline)

AI 기능(채팅·감상문·중간 요약·제목 생성)의 정책값 — 토큰 예약량, 기능별 분당 토큰 몫,
부하 시나리오 — 이 어떤 가정과 계산에서 나왔는지를 한곳에 모은 근거 문서다.
자원 배분(#167)과 토큰 원장(#164) 작업은 이 문서의 값을 출발점으로 쓰고,
값을 바꿀 때는 이 문서를 함께 고친다.

**값의 출처 표기 규칙** — 모든 수치는 셋 중 하나로 표기한다.

- `[사실]` — 코드·설정·계정에서 확인한 값
- `[로컬 계산]` — 실제 도구를 돌려 얻은 값 (운영 데이터 아님)
- `[가정]` — 실데이터 없이 정한 추정값. 운영 데이터가 생기면 교체 대상

> 운영 실측 데이터는 없다. 런칭(2026-06-20) 이력은 있으나 현재 운영 중단 상태이고
> 당시 DB 는 삭제되었다. 사용자 행동 수치는 전부 `[가정]` 이다.

## 고정 사실 [사실]

| 항목 | 값 | 출처 |
|------|----|------|
| 모델 | gpt-4o-mini | application.yml |
| 계정 한도 | 180,000 토큰/분 (TPM) · 9,000 요청/분 (RPM) | application.yml `openai.ratelimit.models` |
| 채팅 메시지 입력 한도 | 4,000자 | `SendMessageRequest` |
| 감상문 편집 한도 | 본문 2,000자 · 제목 50자 | `SummaryEditRequest` |
| 검증 환경 | docker compose 앱 2대 + MySQL 1대 + nginx | 다중 인스턴스 큐 동작 검증용 최소 구성 |

## 한글 토큰 환산율 [로컬 계산]

jtokkit(o200k_base, gpt-4o 계열 인코딩)으로 한글 텍스트 샘플을 계산한 결과:

| 샘플 | 환산율 (토큰/자) |
|------|------|
| 짧은 채팅 문장 (38자) | 0.605 |
| 감상 문장 (71자) | 0.690 |
| 감상문풍 문단 (220자) | 0.618 |
| 영문 용어 섞인 문장 (62자) | 0.516 |
| **종합 (391자 → 240토큰)** | **0.614** |

**계획값은 0.7 토큰/자** 로 쓴다 (여유를 둔 올림값). 한글 100자 ≈ 70토큰.

## 사용자 행동 가정 [가정]

성장 시나리오의 목표 규모다. 현재 규모가 아니며, 아래 도출값은 전부 이 값들에
비례하므로 규모가 다르면 비례 환산하면 된다.

| 항목 | 값 | 근거 |
|------|----|------|
| 일간 활성 사용자 | 10,000명 | 성장 목표 규모 |
| 하루에 채팅 세션을 진행하는 비율 | 20% → 2,000세션/일 | 독서 기록은 매일 하는 활동이 아님 |
| 세션당 사용자 메시지 | 15건 → 30,000건/일 | 감상문에 이르는 이상적 대화 길이 |
| 메시지 평균 길이 | 100자 ≈ 70토큰 | 짧은 감상 위주 대화 |
| 감상문 생성 | 세션의 60% → 1,200건/일 | 대화를 끝까지 마친 세션 비율 |
| 중간 요약 | 세션당 2회 → 4,000건/일 | 컨텍스트 압축 주기에서 유도 |
| 제목 생성 | 세션당 1회 → 2,000건/일 | 세션당 1개 |
| 피크 집중률 | 저녁 1시간에 하루 물량의 10% | 퇴근 후 저녁 시간대 집중. 피크 분당 = 일량 × 10% ÷ 60 ≈ 일량의 0.17% |

## 호출당 토큰 기준값

입력은 `[가정]`(대표 대화 구성 × 환산율 0.7), 출력은 프롬프트로 유도하는 목표 길이와
예약에 쓰는 출력 예약값을 함께 둔다.

| 기능 | 입력 토큰 | 출력 목표 | 출력 예약값 |
|------|------|------|------|
| 채팅 응답 | 2,000 (시스템 프롬프트 + 누적 요약 + 최근 원문 + 새 메시지) | 300 | 600 |
| 감상문 생성 | 3,000 (누적 요약 + 대화 꼬리 전체) | 700 | 1,200 |
| 중간 요약 | 1,500 (직전 요약 + 신규 구간 원문) | 400 | 600 |
| 제목 생성 | 500 | 30 | 100 |

- **기본은 실사용 사후 정산이다.** 확정 차감은 응답의 usage 가 알려주는 실제 토큰으로
  한다. API 의 max_tokens 는 걸지 않는다 — 응답을 중간에 자르는 하드 스톱이라 정보가
  유실된다 (application.yml 주석·컨텍스트 압축 스펙 8절의 기존 결정 유지).
- **출력 예약값**은 자체 사용자 원장을 운영하기 때문에 필요한 예약 계층의 추정치다.
  호출 전에는 출력 크기를 알 수 없으므로 이 값으로 예약을 잡는다:
  예약 = 입력(요청 시점 실계산) + 출력 예약값.
- **예약값은 상한이 아니다.** 실사용이 예약값을 넘을 수 있고, 예약만으로 잔액
  불변식이 보장되지 않는다. 초과분의 정산 처리와 불변식 정의(무엇을 0으로 보장하고
  무엇을 수렴으로 보장하는지)는 원장 설계(#164) 관할.

## 피크 부하 도출

계산식: 기능별 피크 RPM = 일간 건수 × 0.17% / TPM 기여 = RPM × (입력 + 출력 목표).

**보통 시나리오** (위 가정 그대로):

| 기능 | 피크 RPM | 피크 TPM 기여 |
|------|------|------|
| 채팅 응답 | 50 | 115,000 |
| 감상문 생성 | 2 | 7,400 |
| 중간 요약 | 6.7 | 12,700 |
| 제목 생성 | 3.3 | 1,800 |
| **합계** | **62** | **≈ 136,900 (한도의 76%)** |

| 시나리오 | 배수 | 합계 TPM | 상태 |
|------|------|------|------|
| 보통 | ×1 | ≈ 137,000 (76%) | 한도 내. 배분 없이도 동작 |
| 높음 | ×2 | ≈ 274,000 (152%) | 한도 초과. 게이트가 개입, 채팅 몫 보호 필요 |
| 극단 | ×5 | ≈ 685,000 (380%) | 비동기 전면 대기열화, 채팅도 몫 안에서 제한 |

- **TPM 이 첫 병목이다.** RPM 은 극단 시나리오(310 RPM)에서도 한도(9,000)의 3.4%에
  불과하다. 기능별 몫 배분(#167)이 필요한 근거가 여기 있다 — 높음 이상에서 비동기
  작업이 한도를 잠식하면 채팅 응답이 밀린다.
- 채팅 입력 2,000토큰 `[가정]` 이 지배 변수다 (합계의 84%가 채팅). 컨텍스트 압축
  정책이 이 값을 정하므로, 압축 경계가 바뀌면 이 표를 다시 계산한다.

## 정책 초기값

| 정책 | 초기값 | 근거 |
|------|------|------|
| 기능별 TPM 몫 | 채팅 70% (126,000) / 비동기 합산 30% (54,000) | 보통 피크에서 채팅 115,000 < 126,000, 비동기 22,000 < 54,000. 세부 배분·조정은 #167 에서 |
| 토큰 예약량 | 입력(요청 시점 실계산) + 출력 예약값 | 위 표. 원장 설계는 #164 |
| 입력 한도 | 현행 유지 (채팅 4,000자 등) | 상한 초과 시나리오는 게이트·예약이 방어 |

## 민감도

- 모든 도출값은 일간 활성 사용자 수와 피크 집중률에 **선형**이다. 규모 가정이 2배
  틀리면 TPM 도출값도 2배 틀린다 — 그래서 하나의 숫자가 아니라 보통·높음·극단
  3개 시나리오로 검증한다.
- 환산율(0.7)은 올림값이라 실제 부하는 이 표보다 낮은 쪽으로 치우친다.
