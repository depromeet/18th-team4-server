# Test Convention

CLAUDE.md 의 "Testing Conventions" 섹션을 보충하는 상세 문서.

이 문서의 목적은 **테스트 본문을 한 줄씩 읽지 않고도 그 테스트가 좋은지 수초 안에 판단 가능하게** 만드는 것이다. 도구가 테스트를 대량 생성하는 환경에서 검증(리뷰)이 개발의 주 작업이 됐기 때문에, 이 규칙들의 목표는 스타일 통일이 아니라 **리뷰 가능성** 그 자체다. 아래는 권장이 아니라 규범이다 — 위반은 머지 전 수정 대상.

## 1. 테스트 이름은 행위 주장이다

테스트 이름만 위에서 아래로 죽 읽었을 때, 그 클래스가 보장하는 **행위 목록**이 그대로 서야 한다. 이름은 "무엇을 테스트하는가"가 아니라 "무엇이 보장되는가"를 단정문으로 쓴다.

```java
// O — 행위 주장. 이름 목록만으로 명세가 됨
void 폐기된_refresh_token_으로_재발급하면_REUSE_DETECTED_예외가_발생한다()
void 유예_기간_내_토큰은_기존_child_jwtId_로_재서명한다()

// X — 대상만 가리킴. 무엇이 보장되는지 안 드러남
void testRotate()
void refreshToken_test_2()
```

- 한 테스트는 **한 행위**만 단정한다. 이름이 하나의 주장으로 안 써지면 테스트를 쪼갠다.
- 한글 행위 이름을 쓴다 (CLAUDE.md "Testing Conventions").

## 2. 준비(arrange) 상태는 운영 DB 에 존재 가능해야 한다

테스트가 만들어 넣는 엔티티/데이터 상태를 다음 세 분류로 판정한다. **2번 상태를 만드는 테스트는 금지**한다.

1. **운영에서 도달 가능하지만 객체 API 로는 못 만드는 상태** (저장돼야 정해지는 id, 폐기·만료된 RefreshToken 등) → 픽스처로 만드는 게 정당
2. **운영 DB 에 존재할 수 없는 모순 상태** (`nullable=false` 인 `content` 에 null, `issuedAt > expiresAt`, role/status 모순 등) → 만들면 안 됨. 이런 입력에서의 동작을 "검증"하는 테스트는 거짓 커버리지다
3. **객체 API 로는 불가하나 저장소 레벨(JPQL update, 마이그레이션·import 등)에선 발생하는 상태** → 픽스처로 만드는 게 정당

상태의 정당성은 **식별자만 보고 판단 가능**해야 한다. 그래서 픽스처는 모든 필드를 받는 범용 생성이 아니라 유효 상태를 이름으로 드러내는 명명 팩토리만 노출한다 (상세는 CLAUDE.md "Entity Convention").

```java
// O — revokedToken 이라는 이름으로 "운영에 존재 가능한 폐기 상태"가 드러남
RefreshTokenFixture.revokedToken(id, userId, jwtId, issuedAt, expiresAt, revokedAt)

// X — 모든 필드를 받는 범용 생성. 어떤 상태인지·정당한지 본문을 해독해야 앎
RefreshTokenFixture.of(id, userId, jwtId, null, issuedAt, expiresAt, null, null, revokedAt, createdAt)
```

## 3. 구현이 아니라 계약을 단언한다

테스트는 **겉으로 드러나는 결과·계약**(반환값, 던진 예외, 외부 상호작용)을 단언한다. 구현 내부(private 필드, 내부 호출 순서)를 베껴 단언하지 않는다. 구현을 리팩터링해도 계약이 유지되면 테스트는 통과해야 한다.

```java
// X — 내부 필드를 리플렉션으로 단언. 구현 바꾸면 깨지고, 거짓 안정감만 줌
assertThat(ReflectionTestUtils.getField(token, "rotatedAt")).isNotNull();

// O — 계약(공개 동작)을 단언
assertThat(token.isInGrace(now)).isTrue();
```

- 프로덕션 코드에 없는 동작을 테스트만을 위해 노출하지 않는다.
- 예외 검증은 **타입 + ErrorCode 를 함께**, 메서드 레퍼런스로 한다 (리플렉션 문자열 키 금지). 상세 패턴은 [`docs/exception-convention.md`](exception-convention.md) "예외 검증 테스트 패턴".
- 한 테스트가 바꾸는 준비 값은 "기준선과의 차이 하나"만 보이게 한다 — 그 차이가 곧 이 테스트가 검증하는 변수다.

## 4. 존재할 수 없는 상태는 타입으로 막고, 테스트하지 않는다

어떤 상태가 운영에 존재할 수 없다면, 그 입력에서의 방어 동작을 테스트로 검증하는 대신 **타입 차원에서 그 상태를 만들 수 없게** 만든다. 방어 코드를 테스트로 고정하면 방어 코드와 테스트가 영구히 함께 남아 유지비만 든다.

- 판단: "이 분기에 도달하는 입력이 운영에서 만들어질 수 있는가?" 만들어질 수 없다면 enum 값/필드 조합 자체를 제거해 분기를 없앤다.
- 사례: `AiChatMessage.Role` 에서 운영 경로가 절대 쓰지 않는 `SYSTEM` 을 제거 → 조회 쿼리의 role 필터, `HistoryMessage.from()` 의 SYSTEM 분기, 그 검증 테스트가 한꺼번에 사라짐. (2번 "모순 상태 금지"와 같은 원칙)
- 단, 저장소 레벨(2번 분류의 3)에서 실제로 발생 가능한 상태는 타입으로 못 막으므로 이 항목 대상이 아니다.

## 5. 중복 테스트는 삭제한다

커버리지는 **행위·결정 단위**로 채운다. 라인 커버리지 숫자를 좇아 같은 경로를 미세하게 다른 입력으로 반복하지 않는다. 행위가 같으면 테스트 하나로 합치거나 파라미터화하고, 나머지는 **지운다**. 테스트 삭제는 정식 작업이다.

```text
X — 같은 경로(빈 입력 → 빈 결과)를 값만 바꿔 5번 반복
O — 경계가 다른 경우만 남김: 0건 / 1건 / 페이지 경계 / 정렬 동률 tiebreak
```

## 6. 생성된 테스트 리뷰 체크리스트 (규범 관문)

PR 리뷰 시 테스트에 대해 아래를 확인한다. **하나라도 "아니오"면 그 테스트는 머지 전 수정 또는 삭제 대상**이다. 본문 정독 전에 이 고정 질문으로 먼저 거른다 — 양을 양으로 읽지 않는다.

- [ ] 테스트 **이름만** 죽 읽어서 이 도메인이 보장하는 행위 목록이 서는가? 빠진 행위·중복 행위는 없는가? (1·5)
- [ ] 모든 준비(arrange) 상태가 **식별자만 보고** 운영 DB 에 존재 가능하다고 판단되는가? (2)
- [ ] 단언이 계약(반환값/예외/외부 상호작용)을 보는가? 구현 내부(private 필드, 호출 순서)를 베끼지 않았는가? (3)
- [ ] 구현을 리팩터링해도 이 테스트가 살아남는가? (3)
- [ ] 존재 불가 상태를 검증하는 테스트, 또는 지워도 되는 중복은 없는가? (4·5)

리뷰어는 이 다섯 질문으로 통과/탈락을 판정한 뒤, 통과한 것 중 핵심만 본문을 정독한다. 작성자는 PR 올리기 전 같은 체크리스트로 자기 검토한다.

## 7. 테스트가 운영 코드에 영향을 미칠 때의 판단 기준

테스트 편의를 위해 운영 코드를 손대는 변경(접근 제어자 완화, 생성자 노출, getter/setter 추가, 분기 추가 등)을 검토할 때 다음 다섯 질문을 순서대로 통과해야 한다. **2번과 4번에서 동시에 실패하면 그 변경은 test-induced damage — 테스트가 운영을 망가뜨리는 형태 — 로 본다.**

1. **운영 코드를 안 건드리는 대안이 있는가?**
   - 단순히 테스트 작성이 번거로운 문제라면 fixture, test builder, 통합 테스트 등 다른 방법을 먼저 찾는다.

2. **이 변경이 테스트가 아니어도 운영 코드에 도움이 되는가?**
   - 코드가 더 명확해지거나, 불변성이 강해지거나, 의존성이 줄어드는 등 운영 코드 자체의 가치가 있어야 한다.

3. **운영 코드가 어떤 가치를 잃는지 한 문장으로 설명할 수 있는가?**
   - 새로 생기는 위험을 "불변식 우회 가능", "public API 증가", "잘못된 호출 순서 허용" 처럼 한 문장으로 말할 수 있어야 한다. 두루뭉술하면 아직 평가 가능 상태가 아니다.

4. **테스트가 운영 동작을 더 정확하게 검증하게 되는가?**
   - 프로덕션 코드를 바꾼 결과 테스트가 실제 운영 시나리오를 더 잘 검증해야 한다. 반대로 운영에서는 불가능한 상태나 호출 흐름을 쉽게 만들기 위한 변경이라면, 테스트 편의는 늘어도 검증 품질은 낮아질 수 있다.

5. **나중에 되돌리기 쉬운 변경인가?**
   - 테스트 때문에 public 생성자·public setter·범용 public factory 를 추가하면 호출자가 생기는 순간 되돌리기 어려워진다. 반대로 제한된 가시성의 생성자나 테스트 전용 fixture 는 문제가 생겼을 때 비교적 쉽게 되돌릴 수 있다.

### 운영을 망가뜨리는 흔한 형태 (피할 것)

- 내부 상태를 단언하려고 public/protected getter·setter 노출 (3번 "구현이 아니라 계약을 단언" 과 같은 냄새의 반대 방향)
- 운영에서 아무도 호출하지 않는 protected 메서드를 두고 테스트가 override 해서 stub
- 테스트가 mock 으로 null 을 돌리니 운영 코드에 그 null 을 받아주는 방어 분기를 추가
- `@Autowired` 필드 주입 (생성자 주입 대신) — "Spring 슬라이스 테스트 쉽게 하려고"
- 테스트만 부르는 `clearCache()` / `resetState()` / `setForTesting()`

공통점: 운영 API 가 거짓말을 한다. "이 메서드는 운영에서 누가 부르나?" 의 답이 "테스트가 부른다" 면 그건 운영이 모르는 채로 망가진 상태다.
